# 项目更新说明

更新使用新的安装包替换 `/opt/ispweb/current`。域名、证书和已经在服务器上生效的 API 上游保持不变。混淆密钥随新包更换，因为页面和网关必须使用同一次打包生成的密钥。

## 更新

在构建机重新打包：

```bash
./deploy/pack.sh --api http://127.0.0.1:8000
```

把新的 tar.gz 和 `.sha256` 传到服务器后执行：

```bash
sha256sum -c ispweb-1.0.3-新时间戳.tar.gz.sha256
sudo bash ispweb-1.0.3-新时间戳/deploy/update.sh /root/ispweb-1.0.3-新时间戳.tar.gz
```

也可以进入解压目录，直接执行更新脚本。已经装过的机器再执行安装脚本时，也会走同一条升级路径，域名、证书和当前 API 上游保持不变：

```bash
sudo ./deploy/update.sh /root/ispweb-1.0.3-新时间戳.tar.gz
sudo ./deploy/install.sh
```

要在已安装的机器上重新走全新安装（会按本次参数处理证书），加上 `--fresh`。

同时修改后端地址：

```bash
sudo ./deploy/update.sh /root/ispweb-1.0.3-新时间戳.tar.gz --api http://127.0.0.1:8000
```

在仍保留源码和 `vite.config.js` 的机器上，`--api` 会把新地址写回 `vite.config.js`。只放了安装包的服务器没有这个文件，地址写入 `/etc/ispweb/ispweb.env` 和 Nginx 配置注释中的 API 上游。

开启、更换或关闭公网 IP 访问：

```bash
sudo ./deploy/update.sh /root/ispweb-1.0.3-新时间戳.tar.gz --public-ip 1.2.3.4
sudo ./deploy/update.sh /root/ispweb-1.0.3-新时间戳.tar.gz --no-ip-access
```

都不传时沿用 `/etc/ispweb/ispweb.env` 里的 `PUBLIC_IP`。自签证书不会因此重签，用 IP 访问时浏览器会提示证书与地址不符。

## 更新时会发生什么

1. 核对旁边存在的 `.sha256`。
2. 把新版本放到 `/opt/ispweb/releases/rel-<时间>/`。
3. 切换 `/opt/ispweb/current`。
4. 用新包里的密钥覆盖 `/etc/ispweb/ispweb.env` 中的 `URL_GUARD_SECRET`。
5. 按现有域名和证书重新生成 Nginx 配置。
6. 重启 `ispweb-urlguard` 并重载 Nginx。
7. 请求 `http://127.0.0.1:8765/healthz`。失败时自动把程序、环境文件和 Nginx 配置退回更新前。

成功后保留最近的发布目录，并继续保留刚刚替换下来的那一版，便于手工退回。

## 只改 API 地址

后端地址变更且页面代码不变时，不需要重新打包。在服务器上重新执行安装脚本并带上新的 `--api`，或按上一节用更新包加上 `--api`。浏览器里的接口仍然发往门户域名，网关按新的 `API_UPSTREAM` 转发。

## 手工退回

自动回滚没有触发、但新版本页面不正常时：

```bash
ls -ld /opt/ispweb/releases/*
sudo ln -sfn /opt/ispweb/releases/上一版本 /opt/ispweb/current
sudo systemctl restart ispweb-urlguard
sudo nginx -t && sudo systemctl reload nginx
```

退回程序目录后，如果上一版前端使用另一把密钥，还要把 `/etc/ispweb/ispweb.env` 的 `URL_GUARD_SECRET` 改回那一版 `deploy/package.env` 里的值，再重启网关。只改目录、不改密钥时，旧页面的请求会被严格模式拒绝。

## 不需要更新的内容

- 证书续期由 certbot 的系统定时任务处理。80 端口仍保留 `/.well-known/acme-challenge/`。
- 自签证书在域名不变时重复安装会继续使用原来的文件。
- 客户浏览器缓存的是带哈希的静态资源。更新后入口页 `index.html` 为不缓存，刷新即可拿到新页面。
